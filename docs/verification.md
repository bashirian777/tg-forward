## 模拟分块延迟对比

运行命令：`.venv/bin/python -m scripts.benchmark_transfer --size-mb 16 --latency-ms 20`

16 MiB 文件，每个模拟 Telegram 请求固定等待 20 ms，512 KiB 分块，输出文件逐字节检查通过：

| worker 数 | 下载时间（秒） | 上传时间（秒） |
| --- | --- | --- |
| 1 | 0.702 | 0.657 |
| 4 | 0.193 | 0.169 |
| 8 | 0.106 | 0.120 |

这些结果验证并发请求确实能重叠等待，只反映模拟条件，不能作为真实 Telegram 速度或提速倍数。实际性能受网络、数据中心、磁盘、CPU、账号和限流影响。默认设置为 4，可降到 1；小文件实际 worker 数不超过分块数。

## 已验证的故障行为

- 下载中断后补缺失块；已记录块逐块校验 SHA-256，损坏块重新下载。
- 文件预分配大小不能代替分块完整性；成功文件仍检查块和总大小。
- 文件引用过期刷新同一源媒体；源文件已删除／被替换时显示需要人工处理的错误。
- 上传中断保留文件 ID 和已完成分块，继续上传缺失部分；完整文件再次进入下载步骤不改变上传续传身份。
- 取消等待所有 worker 完全退出，避免清理后仍写文件。
- 请求响应丢失后重用持久化 random_id；本地发送成功回执避免再次发送。
- 已上传媒体引用保存在传输目录，最终发送失败可复用；过期引用清除后重新传输。

## 部署后的真实对比

在停止项目服务、释放用户会话后，对同一来源的代表性文档／视频运行：

```bash
.venv/bin/python -m scripts.benchmark_live --task-id YOUR_TASK --message-id SOURCE_MESSAGE_ID --output /path/to/new-report.json
```

脚本与服务共用会话锁，从 `.env` 读取 API 凭据及会话路径，从 SQLite 读取来源任务，并核对登录手机号；依次比较 Telethon 标准传输与并行 1／4／8 worker。源消息应在选定任务的来源中，默认最大 256 MiB，每次传输超时 180 秒；下载内容与标准下载的 SHA-256 比较。上传只保存 Telegram 临时文件分块，不向任何目标频道发送消息。任一传输失败后停止，避免继续叠加限流。

输出含下载和上传耗时、平均速度、CPU 时间、峰值 RSS 与失败类型；重复至少三轮并同时观察实际磁盘、账号 FloodWait 和网络。这个脚本不测最终相册发送、封面或目标权限，这些仍需在部署后的选定任务上验收。测试结束会清理工作目录，再启动项目服务恢复任务。

优先选择稳定值，不以最高瞬时速度决定默认设置。当前 4 是可调整的初始默认值，尚未依据真实网络调优。

已有运行日志和数据库可继续查看，但不能从旧日志推导缺失的历史传输耗时。真实测试尚未执行，仍是现场验收项。

## 保障范围

Telegram 的 random_id 提供服务器去重，但不保证无限期跨重试的 exactly-once。源媒体变更、引用失效、手动调整断点或服务端去重记录失效仍需人工检查。最终发送失败时保留可恢复资料，无法恢复的权限错误显示 error，等待操作员处理。
