# 部署与回退

开发代码与线上进程分开：运行中的旧进程不会自动加载所有新 Python 模块，但静态页面由磁盘提供，刷新可能看到新页面。完整功能需要一次项目服务重启。此文档提供步骤，开发阶段未执行。

## 上线准备

1. 确认项目路径、服务启动方式、当前配置实际临时路径及正在运行的任务。
2. 先停止本项目 Bot／转发进程，等待下载、上传和 SQLite 写入退出。不要停止其他服务，不要停止 PI WEB session daemon。
3. 备份 `config/forwarder.db`、`config/config.json`、`forwarder.session`、`bot_session.session`、当前临时目录及当前 Git 提交。SQLite 有 WAL 时使用 SQLite backup API，或确认进程停止且 checkpoint 完成后复制，不只复制活动主数据库文件。
4. 将备份保存在权限受限的目录，记录备份路径和版本。确认 `.venv` 依赖与 `requirements.txt` 一致。

## 启用新版本

1. 从项目目录使用 `.venv/bin/python -m src.main bot` 或现有服务启动方式，只启动一个使用该 Telegram 登录会话的实例。
2. 首次启动会增加 SQLite revision、处理回执和发送意图表，保留旧任务和进度。
3. 旧 JSON 不覆盖 SQLite；通过后台确认登录有效期、临时目录、分块并发和端口。
4. 登录设置默认 24 小时，下载／上传 worker 默认 4。需要排查网络兼容时先设为 1。
5. 手动启动选定任务，检查发送数量、断点、封面和临时文件；再按验证文档对同一代表性文件做真实速度对比。

## 回退

1. 停止新版本项目进程，等待全部 worker 退出。
2. 保存新版本数据库和临时文件，以便恢复此次部署后的进度。
3. 切回部署前 Git 提交；必要时恢复部署前数据库备份。恢复旧断点可能重发部署期间的内容，需要对照目标消息确认，不能直接假定不会重复。
4. 启动旧版本单实例，检查 Web、Bot 和任务。

旧版本本身含保存配置触发级联删除的问题；回退后避免编辑／保存任务配置，先定位新版本问题并修复。

## 尚待现场验证

- Telegram 实际下载、上传的 1／4／8 worker 吞吐量、CPU、磁盘和 FloodWait。
- 账号所在 DC、媒体 DC 迁移、CDN 路径和目标权限。
- 同一用户曾报告的封面残留操作路径，确认清理反馈与实际目录一致。
